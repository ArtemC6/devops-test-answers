## 1. t.sh, . t.sh, /t.sh, ./t.sh

| Команда | Где ищется файл | Как выполняется | Нужен `+x` |
|---|---|---|---|
| `t.sh` | alias → функция → встроенная команда → каталоги из `$PATH`. Текущий каталог в `$PATH` по умолчанию не входит, поэтому файл рядом **не найдётся**: `command not found` | Отдельный процесс через `execve`: ядро читает shebang и запускает указанный интерпретатор | да |
| `. t.sh` (то же, что `source t.sh`) | Имя без `/` ищется в `$PATH`; bash (не в POSIX-режиме) затем смотрит в текущий каталог. `sh`/`dash` текущий каталог не смотрит | Команды читаются и выполняются **в текущем shell**: переменные, `cd`, `set -e`, `ulimit` остаются после выполнения; `exit` в скрипте закроет текущую сессию (в sourced-скрипте нужен `return`). Shebang игнорируется — это просто комментарий, скрипт всегда выполняется текущим shell | нет, достаточно `+r` |
| `/t.sh` | Абсолютный путь: файл `t.sh` в **корне** файловой системы. `$PATH` не используется | Отдельный процесс, как в первом случае | да |
| `./t.sh` | Относительный путь: файл в **текущем** каталоге. `$PATH` не используется | Отдельный процесс; интерпретатор из shebang. Если shebang нет, bash выполнит файл сам в дочернем процессе | да (и `+r`, интерпретатор читает файл) |

Нюансы, которые встречаются на практике:
- если файловая система смонтирована с `noexec`, `./t.sh` даст `Permission denied`, а `bash t.sh` и `. t.sh` сработают;
- `. t.sh` выполнит bash-ом даже скрипт с `#!/usr/bin/python3` — получится каша из ошибок;
- переменные, которые выставляет `./t.sh`, в родительский shell не попадут — поэтому файлы окружения (`venv/bin/activate`, `.bashrc`) именно «сорсят».

## 2. Ревью bash-скрипта

Исходный скрипт:

```bash
#!/bin/bash

file=$1

if [ -f $file ]
then
    echo "File exists"
else
    echo "File does not exist"
fi
```

Замечания по важности:

1. **`$file` не в кавычках — главная ошибка.**
   - Скрипт запущен без аргумента → `[ -f ]`. У `[` с одним аргументом проверка «строка не пустая», строка `-f` не пустая → истина → скрипт пишет **`File exists`** для пустого пути.
   - Путь с пробелом `my file.txt` → `[ -f my file.txt ]` → ошибка `binary operator expected`, `[` возвращает 2, выполняется `else` — пишет «не существует», хотя файл есть.
   - Путь с `*`, `?`, `[` подвергнется подстановке имён файлов.
   ShellCheck ловит это как SC2086. Решение — `"$file"` или `[[ ... ]]`, внутри которого разбиения на слова нет.
2. **Нет проверки аргументов.** Нужно проверить `$#` и вывести usage.
3. **Код возврата всегда 0.** В автоматизации (cron, CI, `if ./check.sh ...`) результат проверки не узнать. Нужно `exit 1`, когда файла нет, и `exit 2` при неверном вызове.
4. **Ошибки идут в stdout.** Сообщение об ошибке — в stderr (`>&2`).
5. **Семантика `-f`.** `-f` — «существует и это обычный файл» (по симлинку проверяется цель). Для каталога скрипт скажет «File does not exist», хотя путь есть. Нужно либо использовать `-e`, если важен любой путь, либо уточнить сообщение. Я оставил `-f` и поправил текст.
6. Мелочи: имя файла в сообщении, `set -euo pipefail` как привычка, `#!/usr/bin/env bash`.
7. Архитектурное замечание: если дальше файл будут читать, проверка «существует ли» создаёт гонку (TOCTOU) — надёжнее сразу открыть файл и обработать ошибку.

Исправленная версия — [`scripts/check_file.sh`](scripts/check_file.sh):

```bash
#!/usr/bin/env bash
# Проверяет, что путь из первого аргумента существует и это обычный файл.
# Код возврата: 0 — файл есть, 1 — файла нет, 2 — неверный вызов.

set -euo pipefail

if [[ $# -ne 1 || -z $1 ]]; then
    echo "Usage: ${0##*/} <path>" >&2
    exit 2
fi

file=$1

if [[ -f $file ]]; then
    echo "File exists: $file"
else
    echo "File does not exist (or is not a regular file): $file" >&2
    exit 1
fi
```

`file=$1` без кавычек безопасен: в присваивании разбиения на слова нет. Внутри `[[ ]]` кавычки тоже не обязательны. Если нужен POSIX `sh`, то `[ -f "$file" ]` — кавычки обязательны.

## 3. MySQL: простые запросы выполняются медленно

**1. Уточнить у клиента** (5 минут, но экономит час): какие запросы (пример), с какого момента, что менялось (релиз, рост трафика, миграция, обновление MySQL, перенос сервера), медленно всегда или в определённые часы, у всех пользователей или с отдельных серверов приложения.

**2. Проверить, что тормозит именно MySQL**, а не сеть или приложение: выполнить тот же запрос на сервере БД через `mysql` и сравнить время. Если на сервере быстро, смотреть сеть, пул соединений и DNS (обратный резолв при подключении лечится `skip-name-resolve`).

**3. Ресурсы сервера:** `atop`/`top`, `vmstat 1`, `iostat -x 1`, `free -m`:
- iowait и загрузка дисков, задержки (`r_await`/`w_await`);
- swap: если `mysqld` уходит в swap, любые запросы становятся медленными;
- steal на виртуалке, соседи по диску;
- заполненность диска, `dmesg` (ошибки дисков, OOM);
- что ещё работает в это время: бэкап (`mysqldump`, `xtrabackup`), cron, проверка RAID, антивирус.

**4. Состояние MySQL:**
- `SHOW FULL PROCESSLIST` — что выполняется, сколько `Threads_running`, есть ли состояния `Waiting for table metadata lock`, `Locked`, `Sending data`, `Creating sort index`. Простой `SELECT` может висеть за `ALTER TABLE` или за долгой транзакцией, которая держит metadata lock;
- `SHOW ENGINE INNODB STATUS` — lock waits, `History list length` (растёт, когда висит долгая транзакция и purge не успевает), семафоры;
- `information_schema.innodb_trx` — транзакции, открытые давно (часто это забытая сессия или зависший воркер);
- `SHOW GLOBAL STATUS`: `Innodb_buffer_pool_reads` и `Innodb_buffer_pool_read_requests` (промахи buffer pool), `Created_tmp_disk_tables`, `Threads_connected`/`max_connections`, `Table_open_cache_misses`;
- на 5.7 и раньше — включён ли query cache: на нагруженной записи его мьютекс сериализует все запросы, лечится `query_cache_type=0`, `query_cache_size=0`.

**5. Сами запросы:**
- включить slow log (`long_query_time = 0.5–1`, на время диагностики можно `log_queries_not_using_indexes`), собрать за час и прогнать `pt-query-digest` — увидим, что тяжелее всего суммарно;
- `EXPLAIN` / `EXPLAIN ANALYZE` (8.0) для «простых» запросов: часто нет индекса, функция над колонкой в `WHERE`, сравнение строки с числом (неявное приведение отключает индекс), разные кодировки/collation в `JOIN`;
- устаревшая статистика — `ANALYZE TABLE`.

**6. Конфигурация:** `innodb_buffer_pool_size` относительно объёма горячих данных и RAM, `innodb_log_file_size` / `innodb_redo_log_capacity`, `innodb_flush_log_at_trx_commit`, `tmp_table_size`. Для автоматической подсказки — `mysqltuner`, `pt-variable-advisor` (как подсказка, не как истина).

**7. Исправить и подтвердить:** индекс, правка запроса, завершение зависшей транзакции, перенос бэкапа на реплику, увеличение buffer pool или RAM. Каждое изменение по одному, с замером «до/после». Затем дать клиенту короткий отчёт: причина, что сделали, что рекомендуем, и добавить мониторинг (время запросов, `Threads_running`, долгие транзакции, lag реплики), чтобы в следующий раз увидеть проблему раньше клиента.

## 4. Место есть, а файлы не создаются

1. **Закончились inode.** `df -i` покажет `IUse% 100%`. Типичные причины: миллионы мелких файлов — PHP-сессии, кэш, почтовая очередь, временные файлы. Найти каталог: `du --inodes -x / | sort -n | tail` или `find / -xdev -printf '%h\n' | sort | uniq -c | sort -n | tail`.
2. **Квоты.** Пользовательские, групповые или project quota (ext4/XFS) — ошибка `Disk quota exceeded`. Проверка: `quota -v`, `repquota -a`, `xfs_quota -x -c report`.
3. **Квоты контейнера/виртуализации.** В OpenVZ/Virtuozzo у контейнера свои лимиты `diskspace`/`diskinodes` и UBC-лимит на число открытых файлов (`/proc/user_beancounters`, колонка `failcnt`). Изнутри `df` может выглядеть нормально.
4. **Зарезервированные блоки ext4** (по умолчанию 5% для root). Для непривилегированного пользователя место кончается раньше: `Size − Used` выглядит как свободное место, но `Avail` около 0. Проверка: `tune2fs -l /dev/... | grep -i reserved`.
5. **Пишем не туда, куда смотрим `df`.** Каталог — это другой маунт (tmpfs `/tmp` или `/dev/shm` со своим `size=`/`nr_inodes=`, NFS с квотой на стороне сервера, bind-mount, overlay в Docker). Или в каталог писали до монтирования, и данные лежат «под» точкой монтирования. Проверка: `df -h /путь/куда/пишем`, `findmnt -T /путь`.
6. **Особенности файловых систем:**
   - XFS: свободное место есть, но нет непрерывного куска под новый чанк inode (фрагментация), или ФС смонтирована с `inode32` и inode можно размещать только в первом терабайте;
   - Btrfs: закончилось место под метаданные (`btrfs filesystem usage` покажет Metadata full), лечится `btrfs balance`;
   - ext4: переполнен индекс каталога (htree) при огромном числе файлов в одном каталоге — `No space left on device` при создании файла только в этом каталоге, без `large_dir`.
7. **Thin provisioning.** Тонкий LVM-пул (`lvs` — `Data%` 100%), thin-диск гипервизора или SAN закончились физически, а файловая система внутри считает, что место есть. Записи падают с I/O error, ФС может перейти в read-only.
8. **ФС перемонтирована в read-only после ошибок** (`errors=remount-ro`): ошибка будет `Read-only file system`, `df` при этом показывает место. Проверка: `mount | grep ro,`, `dmesg`.
9. Права и атрибуты (`chattr +i` на каталоге, SELinux) дают `Permission denied`/`Operation not permitted`, а не «нет места». Важно сразу смотреть точный текст ошибки.

Обратная ситуация (`df` показывает 100%, `du` — меньше) — это удалённые, но открытые процессом файлы (`lsof +L1`). Это не наш случай, но в диагностике проверяю и его.

## 5. Достаточно ли iostat -x

Нет. `iostat -x` — хорошая отправная точка, но реальную нагрузку по нему одному не оценить:

1. **Первый отчёт — среднее с момента загрузки.** Смотреть надо `iostat -x 1` (или с интервалом) и игнорировать первую выборку.
2. **`%util` вводит в заблуждение на SSD/NVMe, RAID и в СХД.** Это доля времени, когда в очереди был хотя бы один запрос. Устройство, которое обрабатывает запросы параллельно, при 100% util может иметь ещё большой запас. `svctm` давно не считается корректно и удалён в новых sysstat.
3. **Важнее задержки и очередь:** `r_await`/`w_await`, `aqu-sz` (`avgqu-sz`), размеры запросов (`rareq-sz`/`wareq-sz`), IOPS и МБ/с. И их надо сравнивать с возможностями конкретного устройства: 150 IOPS для HDD — предел, для NVMe — ничто.
4. **Не видно, кто нагружает.** Нужны `iotop -o`, `pidstat -d 1`, `atop` (колонки RDDSK/WRDSK), `/proc/<pid>/io`.
5. **Не видно, что за абстракциями.** За md/LVM надо смотреть физические диски по отдельности, за аппаратным RAID — утилиту контроллера (кэш, BBU, состояние rebuild). В виртуалке диск общий с соседями, а в облаке есть лимиты IOPS/МБ/с на диск: при упоре в лимит растёт `await`, хотя «диск» ничем не занят.
6. **Не видно, как нагрузка влияет на систему:** iowait и процессы в состоянии D (`vmstat 1`, `atop`), `/proc/pressure/io` (PSI), объём dirty/writeback-страниц, fsync-нагрузка (`jbd2`).
7. **Нужна история.** Мгновенный срез не показывает тренд и пики — нужны метрики в мониторинге (node_exporter + Prometheus/VictoriaMetrics, Zabbix) и `atop` с историей.

Итог: `iostat -x` с интервалом + задержки и очередь в контексте типа устройства + поиск процессов-источников + картина по iowait/PSI. Только тогда можно сказать, есть ли упор в диск и кто в нём виноват.

## 6. Отказоустойчивое решение с SLA 99.9% для 7 сайтов

### Исходные данные и что значит 99.9%

- 7 сайтов: Nginx, PHP, MySQL, Redis, Memcached.
- Статика: 10 ТБ сейчас, до 50 ТБ через год.
- Базы: 7 × 50 ГБ = 350 ГБ.
- SLA 99.9% — это не более **43 минут простоя в месяц** (8 ч 46 мин в год), включая плановые работы. Значит, любой компонент должен переживать отказ сервера или зоны без ручного вмешательства, а обновления выполняться без остановки.

Доступность последовательной цепочки — произведение доступностей звеньев, поэтому каждое звено (балансировщик, веб, БД, кэш, хранилище) должно быть с запасом выше 99.9%. Это достигается только резервированием.

### Ключевое решение — статика в объектное хранилище

Реплицировать 50 ТБ файлов между серверами (GlusterFS, Ceph, DRBD) дорого и сложно в эксплуатации: нужны минимум 2–3 копии на дисках, ребалансировка при росте, отдельная команда на сопровождение. Поэтому предлагаю:

- хранить статику в **S3-совместимом объектном хранилище** (Yandex Object Storage, Selectel S3). Оно само реплицирует данные, масштабируется без участия клиента, оплата за фактический объём;
- раздавать через **CDN**: снимает трафик с веб-серверов, ускоряет отдачу;
- включить **версионирование** бакета (защита от случайного удаления) и **репликацию** в бакет в другом регионе или у другого провайдера (защита от потери хранилища целиком);
- редко запрашиваемое (старые загрузки) переводить в холодный класс хранения правилами жизненного цикла.

Что потребуется от разработчиков: загрузка файлов через S3 SDK (для популярных CMS есть готовые модули). Переходный вариант — монтирование бакета через `geesefs`/`s3fs`, но это не POSIX-ФС, медленно на мелких операциях, только как временная мера.

### Архитектура (основной вариант — облако, 3 зоны доступности)

```
                 DNS (низкий TTL)
                        │
                       CDN ───────────────► Object Storage (статика, версии, реплика в др. регион)
                        │
         L7-балансировщик облака (TLS, health checks, 3 зоны)
           │                  │                  │
       web-1 (зона A)     web-2 (зона B)     web-3 (зона C)
       nginx + php-fpm    nginx + php-fpm    nginx + php-fpm
       memcached          memcached          memcached
           │                  │                  │
           └──────── Redis (Sentinel, 3 узла) / managed Redis ─────┘
           └──────── MySQL: primary + 2 реплики в разных зонах ────┘
```

**Веб-слой**
- 3 одинаковых веб-сервера в трёх зонах (минимум 2; при трёх отказ одной зоны не перегружает оставшиеся). Конфигурация — Ansible, никаких ручных изменений.
- Для каждого из 7 сайтов — отдельный пул php-fpm под отдельным пользователем: изоляция и раздельные лимиты.
- Код не лежит на общей ФС: CI/CD (GitLab CI) собирает релиз и раскатывает его на все узлы с атомарным переключением симлинка и `reload` php-fpm. Деплой и обновления ОС — поочерёдно, с выводом узла из балансировки.
- Сессии PHP — в Redis, чтобы пользователь не терял сессию при переключении узла.
- Балансировщик облака сам распределён по зонам. На своих серверах вместо него — пара nginx/HAProxy с keepalived (VRRP) и плавающим IP.
- Если у клиента или у нас есть компетенция и желание — тот же слой можно разместить в Managed Kubernetes (Deployment на сайт, HPA). Для 7 PHP-сайтов это оправдано, если ожидается рост числа проектов. Иначе VM + Ansible проще и дешевле в поддержке.

**MySQL (350 ГБ, растёт)**
- Вариант 1, рекомендую: **управляемый MySQL** облака — кластер из 3 хостов в разных зонах, автоматический failover, бэкапы и PITR от провайдера. Меньше всего операционных рисков.
- Вариант 2, своё: primary + 2 реплики (GTID, semi-sync, чтобы не терять подтверждённые транзакции), автоматическое переключение через Orchestrator, приложения ходят через ProxySQL на веб-узлах, который знает текущий primary. Альтернатива — Percona XtraDB Cluster из 3 узлов с записью в один узел через ProxySQL.
- Узлы: NVMe/SSD, около 1 ТБ (данные + бинлоги + запас на рост и `ALTER`), RAM 64–128 ГБ — чтобы горячая часть данных помещалась в buffer pool. Точный размер — после снятия профиля нагрузки.
- Бэкапы: ежедневный `xtrabackup` + непрерывное копирование бинлогов (восстановление на любой момент), хранение в S3 в другом регионе, **регулярная проверка восстановления** (бэкап без проверенного восстановления не считается бэкапом).
- 7 баз в одном кластере, с отдельными пользователями и правами на каждую. Если один сайт заметно тяжелее — вынести его в отдельный кластер.

**Redis**
- Если в Redis сессии/очереди — 3 узла с Sentinel (или managed Redis с репликой в другой зоне), приложение подключается через Sentinel-aware клиент.
- Если только кэш — достаточно реплики, но проще сразу делать одинаково.

**Memcached**
- Чистый кэш, реплицировать не нужно. Экземпляр на каждом веб-узле, в приложении — список всех серверов с консистентным хешированием (`Memcached::OPT_LIBKETAMA_COMPATIBLE`). Падение узла даёт только промахи кэша.
- Отдельно стоит обсудить с разработчиками, нужен ли Memcached при наличии Redis — меньше компонентов, меньше точек отказа.

**Мониторинг и эксплуатация (без этого 99.9% не обеспечить)**
- Метрики: Prometheus/VictoriaMetrics + Grafana (node, nginx, php-fpm, MySQL, Redis exporters), внешние HTTP-проверки каждого сайта из нескольких точек, алерты дежурной смене 24/7.
- Логи централизованно (Loki/ELK).
- Runbook на типовые аварии, учения по переключению БД и отключению зоны раз в квартал.
- Плановые работы — только без простоя (rolling), изменения через Git и CI.

**Стартовая конфигурация** (уточняется после замера текущей нагрузки):

| Роль | Кол-во | Ресурсы |
|---|---|---|
| Веб (nginx + php-fpm + memcached) | 3 | 8 vCPU, 16 ГБ RAM, 50 ГБ SSD |

## 7. Сервер под БД логов и аналитики

### Характер нагрузки
Логи действий — это вставка без изменений (append-only), огромное число строк и аналитические запросы с агрегацией по большим диапазонам времени. Строковые OLTP-СУБД (MySQL/PostgreSQL) здесь работают плохо: аналитика читает целые строки с диска, индексы на каждый вариант отчёта не напасёшься, 900 ГБ за полгода будут постоянно расти.

### Рекомендация по СУБД: ClickHouse
- Колоночное хранение и сжатие: на логах объём на диске обычно в разы меньше исходного. Точный коэффициент проверяем на выгрузке реальных данных.
- Агрегации по миллиардам строк за секунды, параллельно на всех ядрах.
- Удаление старых данных через `TTL` и `DROP PARTITION` — мгновенно, без тяжёлых `DELETE`.

### Рекомендации по серверу
- **CPU:** 16–32 ядра — ClickHouse распараллеливает запрос по ядрам, аналитика упирается в CPU и диск.
- **RAM:** 64–128 ГБ. Память нужна под `GROUP BY`/`JOIN` и кэш файловой системы. Под хранение всего объёма RAM не нужна.
- **Диски:** NVMe SSD в RAID1/RAID10 под горячие данные (последние 1–3 месяца) с запасом ×2 к прогнозу — фоновые слияния (merge) временно требуют свободного места. Холодные партиции можно переносить на HDD через `TTL ... TO VOLUME 'cold'` (storage policy) или в S3.
- **Сеть:** 10 Гбит/с, если будет реплика.
- **Отказоустойчивость:** вторая реплика (`ReplicatedMergeTree` + ClickHouse Keeper из 3 узлов, Keeper можно разместить на небольших VM). Без реплики — хотя бы регулярный `clickhouse-backup` в S3.

### Настройка БД
- Схема таблицы:
  ```sql
  CREATE TABLE events
  (
      event_time  DateTime64(3) CODEC(Delta, ZSTD),
      event_date  Date DEFAULT toDate(event_time),
      event_type  LowCardinality(String),
      user_id     UInt64,
      session_id  String,
      url         String CODEC(ZSTD(3)),
      ip          IPv6,
      user_agent  String CODEC(ZSTD(3)),
      payload     String CODEC(ZSTD(3))
  )
  ENGINE = MergeTree
  PARTITION BY toYYYYMM(event_date)
  ORDER BY (event_type, event_date, user_id)
  TTL event_date + INTERVAL 12 MONTH DELETE;
  ```
  `ORDER BY` выбирается под самые частые фильтры отчётов, партиции — по месяцу, срок хранения — по договорённости с клиентом.
- **Вставка пачками** (тысячи строк, не по одной): события пишутся в очередь (Kafka/Redpanda или Vector) и вставляются батчами, либо включается `async_insert=1`. Сайт не должен синхронно ждать запись лога — логирование не должно замедлять и ронять сайт.
- **Материализованные представления** для частых отчётов (агрегаты по часам/дням) — дашборды читают маленькие таблицы.
- **Ограничения для аналитиков:** отдельный пользователь с профилем `readonly`, `max_memory_usage`, `max_execution_time`, квоты — один тяжёлый запрос не должен положить сервер.
- **BI:** Grafana, Superset, DataLens — подключаются к ClickHouse напрямую.
- **Мониторинг:** встроенный Prometheus-эндпоинт ClickHouse, алерты на место, число частей в партиции (`Too many parts`), отставание реплик.

### Если клиент хочет остаться на MySQL
- Отдельный сервер (не основной БД сайта) и отдельная реплика, на которой строится аналитика, чтобы отчёты не мешали записи.
- Таблица с `PARTITION BY RANGE` по дате: старые данные удаляются `DROP PARTITION`, а не `DELETE`.
- Минимум индексов (каждый замедляет вставку), первичный ключ — автоинкремент или `(дата, id)`.
- `innodb_buffer_pool_size` — 70–75% RAM, увеличенный redo log, `innodb_flush_log_at_trx_commit=2` (для логов допустима потеря последней секунды при падении ОС), вставки пачками, сжатие страниц (`ROW_FORMAT=COMPRESSED`).
- Сервер: NVMe в RAID10, RAM 128 ГБ+.
- При этом сложные отчёты по всему объёму всё равно будут работать минутами — честно предупреждаю клиента и предлагаю ClickHouse.

**Вопросы к клиенту:** поток событий (событий/с, пики), сколько хранить, какие отчёты нужны и как быстро, кто и чем строит отчёты, допустима ли потеря части логов.

## 8. Блокировка запросов GET /?[a-z]{16} в Nginx

Это типичный флуд со случайной строкой запроса — так обходят кэш, чтобы каждый запрос доходил до PHP. Блокирую на трёх уровнях.

**1. Nginx — отклонить до бэкенда.** Конфиг: [`nginx/block-random-query.conf`](nginx/block-random-query.conf).

```nginx
# контекст http {}
map "$request_method $request_uri" $block_random_query {
    default                    0;
    "~^GET /\?[a-z]{16}$"      1;
}

# в server {}
if ($block_random_query) {
    return 444;
}
```

- `$request_uri` — исходный URI вместе со строкой запроса (`$uri` её не содержит, а `location` по аргументам не матчится).
- Регулярка с якорями `^...$`: ровно 16 строчных букв, без `=` и `&`, поэтому обычные ссылки вида `/?utm_source=...` не задеваются. Перед включением проверяю по access-логу, что легитимных запросов под шаблон нет (`grep -cE '"GET /\?[a-z]{16} HTTP' access.log` и разбор нескольких IP вручную).
- `map` вычисляется лениво и один раз, `if` с `return` на уровне `server` — безопасное использование `if`.
- `444` — nginx закрывает соединение без ответа: ни байта трафика и никакой работы PHP. Если нужен понятный ответ для отладки — `403`.
- Сопоставляю метод и URI, а не `$request`: в HTTP/2 строка протокола будет `HTTP/2.0`, и правило по `$request` с `HTTP/1.1` атакующий обойдёт.

Применение: `nginx -t && systemctl reload nginx`, проверка через `curl` (команды есть в файле конфига).

**2. Файрвол — чтобы ботнет не занимал воркеры nginx.** Nginx всё равно принимает TCP/TLS и разбирает запрос. Если IP немного, их банит fail2ban по записям с кодом 444: [`fail2ban/filter.d/nginx-random-query.conf`](fail2ban/filter.d/nginx-random-query.conf) и [`fail2ban/jail.d/nginx-random-query.local`](fail2ban/jail.d/nginx-random-query.local) (лучше с действием на ipset/nftables, чтобы тысячи IP не превращались в тысячи правил iptables). Проверка фильтра: `fail2ban-regex /var/log/nginx/access.log /etc/fail2ban/filter.d/nginx-random-query.conf`.

**3. Если атака большая** (каналы или CPU на TLS забиты) — фильтрация на стороне провайдера/сервиса защиты от DDoS или правило в WAF/CDN. Плюс общие меры: `limit_req`/`limit_conn` на динамику и кэширование главной страницы с ключом без случайных аргументов.

## 9. Самый тяжёлый запрос MySQL

Из лога:

| # | Запрос | Query_time | Lock_time | Rows_examined | Rows_sent |
|---|---|---|---|---|---|
| 1 | SELECT (лента форума), 1 форум, `LIMIT 100` | 2.18 s | 0.0001 | 324 036 | 0 |
| 2 | `DELETE FROM phpbb_post_revisions WHERE post_id = …` | **9.26 s** | 0.00002 | 948 209 | 0 |
| 3 | SELECT, 4 форума, без лимита | 1.11 s | 0.0002 | 521 597 | 7 |
| 4 | SELECT, ~140 форумов, без лимита | 4.68 s | 0.0002 | **2 457 916** | 1 |

**Ответ: самый тяжёлый — запрос №4.** Он перебрал 2,46 млн строк, чтобы вернуть одну. Это больше всего реальной работы для сервера (CPU, buffer pool, диск).

Как я это определил:
- **`Query_time` — не мера тяжести.** Это время «по стене часов», в него входит ожидание: блокировки строк InnoDB (в MySQL/Percona до 8.0.28 они не попадают в `Lock_time`, там только табличные блокировки; формат этого лога — Percona Server 2021 года), очередь на диск, конкуренция с другими запросами. У `DELETE` №2 максимальное время, но строк просмотрено в 2,6 раза меньше, чем у №4: 9 секунд на миллион строк для простого удаления означают, что он большей частью ждал, а не работал.
- **`Rows_examined`** не зависит от фоновой нагрузки и показывает, сколько строк движок прочитал — у №4 он максимальный. `Lock_time` у всех ничтожный, значит, ожидание табличных блокировок ни при чём.
- Отношение «просмотрено/отправлено»: 2,46 млн на 1 строку — признак отсутствия подходящего индекса.
- Если смотреть **по шаблону запроса** (как группирует `pt-query-digest`), то №1, №3 и №4 — один и тот же запрос phpBB с разными параметрами. Суммарно он дал 7,98 с и 3,3 млн просмотренных строк — это главный кандидат на оптимизацию. На полном slow log я бы начал именно с `pt-query-digest slow.log` и смотрел колонки Response time (сумма) и Rows examine.

Почему он тяжёлый и что сделать:
- `ORDER BY t.topic_last_post_time DESC, p.post_time` — сортировка по колонкам из двух разных таблиц, индекс использовать нельзя: временная таблица + filesort по всем подходящим строкам. `LIMIT 18446744073709551615` — это «без лимита», так phpBB пишет запрос без ограничения.
- Фильтр `p.forum_id IN (...) AND p.post_approved = 1 AND p.post_time > X` — нужен составной индекс:
  ```sql
  ALTER TABLE phpbb_posts ADD INDEX forum_approved_time (forum_id, post_approved, post_time);
  ```
  (добавлять через `pt-online-schema-change`/`gh-ost` или `ALGORITHM=INPLACE, LOCK=NONE`, сначала проверить `EXPLAIN` на копии/реплике).
- Проверить план: `EXPLAIN FORMAT=JSON` / `EXPLAIN ANALYZE` и `SHOW INDEX FROM phpbb_posts`.

**Отдельно про `DELETE` №2** — он хоть и не самый тяжёлый по работе, но опасный: 948 тыс. просмотренных строк для удаления по `post_id` означают, что индекса по `post_id` в `phpbb_post_revisions` нет (это таблица расширения, не стандартная). В InnoDB такой `DELETE` при полном сканировании ставит блокировки на просмотренные строки и на 9 секунд блокирует запись в таблицу остальным. Лечится индексом:
```sql
ALTER TABLE phpbb_post_revisions ADD INDEX post_id (post_id);
```

## 10. Что происходит на сервере (скриншот 1, ds01)

**Ответ клиенту:**

> Здравствуйте!
>
> Разобрали состояние сервера ds01 на 04.07.2021 00:01 (снимок atop за 60 секунд).
>
> **Что происходит.** Сервер упирается в диски, а не в процессор или память. На сервере два программных RAID1-массива, и на обоих идёт проверка целостности (процессы `md5_resync` и `md0_resync`, `md5_raid1`, `md0_raid1`):
> - диски `sdc` и `sdd` (массив md5) почти полностью заняты проверкой: каждый ~145 МБ/с последовательного чтения, нагрузка 89–96%, записи почти нет — это именно проверка (check), а не восстановление массива;
> - на дисках `sda` и `sdb` (массив md0) также идёт проверка, около 20 МБ/с.
>
> Из-за этого процессы, которым нужен диск (сайты, база данных), ждут в очереди: процессорное время ожидания диска (iowait) — 389%, то есть в среднем около 4 из 12 ядер простаивают в ожидании дисков. Средняя нагрузка (load average) 29–36 при 12 ядрах — следствие этого ожидания, а не нехватки CPU. Память в порядке: 45 ГБ занимает кэш, swap почти не используется.
>
> Время снимка — ночь на воскресенье. Проверку массивов в это время обычно запускает плановое задание (`raid-check` / `checkarray` по cron): это штатная процедура, она находит битые сектора до того, как они приведут к потере данных.
>
> **На что стоит обратить внимание отдельно.**
> 1. **Диск `sdb` работает заметно хуже своей пары `sda`.** При одинаковом числе операций (~17,5 тыс. чтений и ~760 записей за минуту у каждого) `sdb` занят на 99% со средним временем операции 3,2 мс, а `sda` — на 22% и 0,7 мс. Это частый ранний признак деградации диска (переназначенные сектора, ошибки чтения, проблемы кабеля/порта). Предлагаем проверить SMART и системный журнал и, если подтвердится, заранее заменить диск, пока массив цел.
> 2. **Несколько копий `denyhosts`** работают одновременно и вместе пишут на диск ~17 МБ в минуту. Скорее всего, это экземпляры в разных контейнерах. Инструмент устарел и не поддерживается.
> 3. **Множество короткоживущих процессов `php`** от пользователя apache (около 1 300 запусков процессов в минуту на сервере) — похоже на запуск PHP в режиме CGI, когда на каждый запрос стартует новый процесс.
>
> **Предложения.**
> 1. Сейчас: при необходимости снизить влияние проверки на сайты — ограничить её скорость (`/sys/block/md5/md/sync_speed_max` или глобально `dev.raid.speed_limit_max`). Останавливать проверку совсем не рекомендуем.
> 2. Перенести плановую проверку на самое тихое время по графикам трафика (расписание — в `/etc/cron.d/raid-check`, параметры — в `/etc/sysconfig/raid-check`) и постоянно ограничить её скорость через `dev.raid.speed_limit_max` в `sysctl.conf`.
> 3. Включить на массивах write-intent bitmap (`mdadm --grow --bitmap=internal /dev/mdX`): после аварийной перезагрузки ресинхронизация займёт минуты, а не часы полного прохода по дискам.
> 4. Проверить `sdb`: `smartctl -a /dev/sdb` (Reallocated/Pending/Uncorrectable sectors, CRC errors), `dmesg` на ошибки ATA; при подтверждении — плановая замена.
> 5. Заменить `denyhosts` на fail2ban с блокировкой через ipset/nftables (или ограничить SSH по IP и ключам) — один процесс на сервере вместо нескольких.
> 6. Если PHP действительно работает как CGI — перевести сайты на php-fpm: меньше процессов, меньше нагрузки на CPU и диск.
> 7. На будущее — алерты на iowait, загрузку и время отклика дисков, а также на ход проверки RAID, чтобы видеть такие ситуации в мониторинге заранее.

Что я посмотрю на сервере, чтобы подтвердить выводы: `cat /proc/mdstat` (должно быть `check`), `cat /sys/block/md*/md/sync_action`, задание в `/etc/cron.d/`, `smartctl -a /dev/sdb`, `atop -r` за предыдущие часы — когда началась проверка и как менялась нагрузка.

> - Load average 79 → 56 → 24 (за 15, 5 и 1 минуту): 10–15 минут назад было значительно хуже, сейчас нагрузка спадает. Вероятно, был всплеск потребления памяти, который вытеснил данные в swap, и сервер до сих пор «отыгрывает» его чтением с диска.
>
> **Что работает на сервере.** Судя по процессам: два экземпляра MySQL (88 и 161 потоков), GitLab (`bundle` — Puma/Sidekiq, свой PostgreSQL, Redis, Prometheus, gitlab-exporter), Apache. Всё это делит 31 ГБ памяти и один диск. Один GitLab с полным набором компонентов требует от 8 ГБ и больше.
>
> Также по системным процессам видно старое ядро 2.6.32 (OpenVZ/CentOS 6) — эта ОС больше не получает обновлений безопасности. Отдельного RAID нет — один диск `sda` является единой точкой отказа.
>
> **Предложения.**
>
> Сразу:
> 1. Найти, кто и когда занял память: история atop за последний час (`atop -r`), сортировка по памяти; кто сидит в swap (`VmSwap` в `/proc/<pid>/status`); не было ли OOM в `dmesg`.
> 2. Привести лимиты памяти в соответствие с сервером:
>    - для обоих MySQL — `innodb_buffer_pool_size` и число соединений так, чтобы в сумме они не выходили за выделенный им объём;
>    - для GitLab — уменьшить число воркеров Puma и параллельность Sidekiq, отключить встроенный мониторинг, если он не используется (`prometheus_monitoring['enable'] = false`), умерить `shared_buffers` его PostgreSQL;
>    - лимиты памяти контейнеров.
> 3. После того как память освободится — вернуть вытесненное из swap в спокойное время (`swapoff -a && swapon -a`, только при достаточном объёме свободной памяти).
>
> В ближайшее время:
> 4. Вынести GitLab на отдельный сервер/VM — у него свой профиль нагрузки и пиковые задачи (CI, бэкапы, импорт), которые не должны влиять на сайты и базы.
> 5. Увеличить память (например, до 64 ГБ) и перейти с HDD на SSD/NVMe в RAID1: случайное чтение на SSD в сотни раз быстрее, а RAID1 защитит от потери данных при отказе диска.
> 6. Спланировать переезд с CentOS 6 / OpenVZ 6 на поддерживаемую ОС (AlmaLinux/Rocky Linux) и современную виртуализацию.
> 7. Мониторинг: алерты на использование swap, swap-in, iowait и занятость диска, чтобы реагировать до того, как сайты начнут тормозить. Включить process accounting для atop (сейчас «no procacct»), чтобы видеть и короткоживущие процессы.

## 13. count(*) = 5, а LIKE даёт 7

```sql
SELECT count(*) FROM tickets_messages WHERE ticket_id = 56412;        -- 5
SELECT count(*) FROM tickets_messages WHERE ticket_id LIKE '%56412';  -- 7
```

По условию других значений, оканчивающихся на 56412, нет, перед числом символов нет. Значит, оба запроса должны находить одни и те же 7 строк. Разница в том, **как** MySQL их ищет:
- `ticket_id = 56412` — поиск по индексу на `ticket_id` (`type: ref`);
- `LIKE '%56412'` — шаблон с ведущим `%` индекс использовать не может → полное сканирование таблицы (кластерного индекса).

**Наиболее вероятная причина — вторичный индекс по `ticket_id` рассинхронизирован с данными (повреждён).** В нём нет двух записей, которые есть в самой таблице. Для MyISAM — после аварийного завершения, для InnoDB — после сбоя железа/ФС, бага или неудачного восстановления. Сюда же относится вариант с партиционированной таблицей, у которой строки оказались не в той партиции: `=` отбрасывает «лишние» партиции (partition pruning), а `LIKE` просматривает все.

Если бы `ticket_id` был строковым, `= 56412` сравнивал бы числа, индекс не использовал бы и тоже нашёл бы все 7 строк — это ещё один аргумент за версию с индексом.

**Мои действия:**

1. Структура и планы:
   ```sql
   SHOW CREATE TABLE tickets_messages\G
   EXPLAIN SELECT count(*) FROM tickets_messages WHERE ticket_id = 56412;
   EXPLAIN SELECT count(*) FROM tickets_messages WHERE ticket_id LIKE '%56412';
   ```
   Ожидаю: первый — по индексу, второй — `ALL`.
2. Тот же запрос в обход индекса:
   ```sql
   SELECT count(*) FROM tickets_messages IGNORE INDEX (<имя_индекса>) WHERE ticket_id = 56412;
   ```
   Если вернёт 7 — версия с индексом подтверждена.
3. Найти «потерянные» строки: сравнить id из обоих запросов
   ```sql
   SELECT id, ticket_id, HEX(ticket_id) FROM tickets_messages WHERE ticket_id LIKE '%56412';
   ```
   и посмотреть, когда и как они появились (даты, особенности вставки).
4. Исключить простые причины: оба запроса выполнялись на одном и том же сервере (не мастер/реплика через прокси), не внутри старой транзакции с REPEATABLE READ (снимок данных), не из query cache (MySQL ≤ 5.7), между запросами не было вставок.
5. Проверка таблицы: `CHECK TABLE tickets_messages EXTENDED;` и журнал ошибок MySQL (сообщения о corruption).
6. Исправление — после свежего бэкапа:
   - InnoDB: пересоздать таблицу (`ALTER TABLE tickets_messages ENGINE=InnoDB;` / `OPTIMIZE TABLE`, на большой таблице — `pt-online-schema-change`) или пересоздать индекс (`DROP INDEX` + `ADD INDEX`);
   - MyISAM: `REPAIR TABLE tickets_messages;` и план перевода на InnoDB.
7. Найти первопричину и масштаб: `CHECK TABLE` остальных таблиц, ошибки дисков и памяти (`dmesg`, SMART, ECC), сравнение мастера и реплик (`pt-table-checksum`), не было ли аварийных перезагрузок. Повреждённый индекс в одной таблице — повод проверить всю базу.
8. Сообщить клиенту: что нашли, какие данные затронуты, что исправили и что сделали, чтобы не повторилось (мониторинг ошибок MySQL, проверка дисков, регулярные `CHECK TABLE`/checksum на репликах).
